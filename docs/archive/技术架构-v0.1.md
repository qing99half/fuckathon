# 《预制黑客松模拟器》技术架构 v0.1
## —— 轻量化代码 × 最小化 debug 工作量

> 核心判断：本游戏 **90% 是内容（JSON 文案/数值），10% 是引擎**。
> 因此架构目标不是"写强大的代码"，而是：
> **① 引擎薄到不需要 debug；② 内容错误在构建期被拦下，不进运行时；③ 任何 bug 可以一键复现。**

---

## 1. 技术选型：Vanilla TypeScript + Vite，零运行时依赖

**推翻 v0.9 草案中的 React + Tailwind**，理由：

| 考量 | React 方案 | Vanilla TS 方案 |
|---|---|---|
| 运行时依赖 | react+react-dom ~45KB + 心智负担 | **0 KB** |
| Bug 类别 | 多一类：状态不同步、hooks 依赖、重渲染 | 只有"我的逻辑错"一类 |
| UI 复杂度匹配 | 本游戏 UI = 卡片+HUD+弹幕+Canvas，组件不到 10 个 | 完全够用 |
| 构建配置 | JSX/Tailwind 配置链 | Vite 开箱即用，CSS 手写（设计系统本来就小） |

UI 用**模板函数 + 直接 DOM 更新**（每屏一次全量重绘当前卡片，没有局部 diff 需求），
CSS 手写一份 ~300 行的设计 token + 组件样式。没有框架 = 没有框架的 bug。

---

## 2. 最重要的架构约束：引擎不碰 DOM

```
engine/（纯 TS，Node 可跑，零 DOM 依赖）
├── rng.ts        # 种子随机数（见 §3）
├── state.ts      # RunState 定义 + 创建
├── effects.ts    # 应用选项效果（纯函数）
├── deck.ts       # 卡组组装：主线 + 条件事件 + 概率事件掷骰
├── judge.ts      # 评审期计算模型
├── ending.ts     # 结局规则引擎
└── index.ts      # 唯一入口：next(state, choiceId) → {state, viewEvents[]}

ui/（渲染层，只订阅 viewEvents）
├── card.ts / hud.ts / barrage.ts / pixelscene.ts / endingcard.ts / audio.ts
```

- 引擎输入输出都是纯数据：`(当前状态, 玩家选项) → (新状态, 视图事件列表)`
- UI 层只负责把 viewEvents 画出来；**UI 没有自己的状态逻辑**
- 好处：引擎可以脱离浏览器在 Node 里跑 → 这是 §4 机器人测试和 §3 复现的前提

---

## 3. 可复现性：种子随机 + 选择日志（debug 成本杀手）

1. **种子随机数**：每局开始生成 seed（如 `KAO-4F2A`），所有掷骰走这个 seed 的 PRNG
2. **选择日志**：每次选择追加 `{cardId, optionId}` 到 `state.log`
3. **重放**：`replay(seed, log)` 可以精确重建任何一局 →
   - 玩家报 bug 只需报"种子 + 你点了什么"
   - 自己测试：发现坏局，存下 seed+log，修好后重放验证
4. **调试模式**：URL 加 `?debug=1` → 屏幕角落显示 seed、全部隐藏数值、可跳转任意阶段。
   开发期 debug 全靠它，不进生产逻辑

## 4. 内容错误的三道拦截（把 debug 消灭在写文案阶段）

### 第一道：构建期内容校验（`scripts/validate.ts`）
`npm run build` 前先跑校验，失败则构建失败。检查：
- 每个 `cardId` / `optionId` / `nextId` 引用存在
- 每个结局条件引用的数值键存在
- 每张事件卡至少 2 个选项；每个选项的数值幅度符合四档阶梯（±5/10/20/30-40，超标报警）
- 概率字段必须是 0-1 死数，禁止空/模糊
- 文案字数上限（标题 ≤20 字、正文 ≤60 字——保护 UI 不炸版）

### 第二道：机器人模拟器（`scripts/simulate.ts`，Node 直接跑引擎）
```bash
npm run simulate 1000
```
- 用 1000 个随机种子各跑一局（机器人随机/极端策略乱点），断言不变量：
  - 每局必然到达某个结局（没有死胡同）
  - money 永不为负（预算硬约束生效）
  - 没有任何卡抛出异常；13 个结局全部被至少命中一次（结局不可达 = 条件写错了）
- **内容改完跑一次，30 秒替代数小时手测**

### 第三道：运行时兜底
开发模式：卡片渲染异常 → 全屏显示 cardId 和错误（立刻定位到 JSON 行）
生产模式：跳过异常卡片进下一张 + console 记录（玩家无感，事后可查）

## 5. 系统间解耦：单向事件流

```
玩家点击 → engine.next() → viewEvents[]
                              ├→ HUD: 数值跳动
                              ├→ 弹幕层: 推联动弹幕
                              ├→ 音频: 切 BGM / 播 SFX
                              ├→ 像素场景: 换地图/昼夜/小人数量
                              └→ 结局页: 渲染结局卡
```

- 各 UI 模块只订阅事件、互不调用 → 改弹幕不会碰坏音频
- 像素场景是**纯只读消费者**（读 venue/人数/怨气/昼夜），永远不写状态

---

## 6. 资产管线：一次性脚本，产物入库

- `scripts/build-assets.py`：调色板归一 → PNG-8 压缩 → 图集合并 → 字体子集化（从 JSON 文案自动提取字符表）
- 产物直接 commit 进 `public/assets/`，运行时零处理、零依赖
- 美术资源改了 = 重跑脚本 + commit，代码不动

---

## 7. 体积预算（代码侧）

| 部分 | 预算行数 |
|---|---|
| engine/ 全部 | ≤ 800 行 |
| ui/ 全部 | ≤ 1500 行 |
| CSS | ≤ 400 行 |
| scripts/ | ≤ 400 行 |
| **合计** | **≤ 3100 行**（内容 JSON 不计） |

行数超标 = 设计变复杂了的信号，先砍设计再加代码。

---

## 8. 部署与迭代

- GitHub + Vercel 静态托管，`npm run build` = validate + vite build + asset check
- 加梗/改数值/调概率 = 改 JSON → `npm run simulate 200` → push → 自动部署
- localStorage 仅存：图鉴进度 + 当前局存档（state+log 序列化，刷新可续局）

---

## 9. 明确不做的事（防止复杂度爬进来）

- ❌ 不做账号/后端/排行榜（传播靠结局卡图片，不靠社交系统）
- ❌ 不做多语言（梗翻译不了，只做中文）
- ❌ 不做动画引擎/粒子系统（CSS transition + Canvas 基础绘制足够）
- ❌ 不引入状态管理库、路由库、UI 组件库（单页单流程，URL 只用于 ?debug）
- ❌ 不做运行时降级双实现（owner 已拍板，性能靠资源纪律）
